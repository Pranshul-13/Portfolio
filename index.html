E/02 Founder · Jun 2026 - Present

QuickLearn

An adaptive SAT prep platform that routes each student toward the practice that moves them most.

Role
Founder - product, ML, and infrastructure
Status
Live · 35 beta users
Stack
Next.js · Supabase · PyTorch · ONNX Runtime · FastAPI · Cloudflare Workers · Git-based CI/CD
  • The hard part of adaptive practice isn't showing questions, it's knowing what a student actually knows. QuickLearn models that in three layers that hand off to each other as evidence accumulates: a rules engine sorts new students into one of six personas, K-Means++ with power-iteration PCA places them against the cohort, and once there are enough attempts a Transformer takes over. Each layer owns a panel on the dashboard, so the student can see which one is currently driving their recommendations. The IRT 3PL and K-Means priors are what cold-start students who have no history.
  • The knowledge-tracing model is a 4-layer, 8-head Transformer with two prediction heads: one estimates whether the next question in a given domain will be answered correctly, the other emits a per-domain mastery vector. Raw model confidence is badly calibrated, so an isotonic regression stage sits on the output and turns scores into probabilities that mean what they say.
  • Serving it honestly was the interesting constraint. The model trains in PyTorch, exports to ONNX at opset 18 with a dynamic batch axis, and is served by FastAPI on Render behind a bearer token, with the artifact in object storage and a partial unique index in Postgres guaranteeing exactly one active model version. Reads go cache first, then live inference, then a cluster prior, so if the sidecar is unreachable the dashboard degrades to a worse answer instead of an error. Scoring per-domain mastery runs at p95 14 ms across 8 forward passes per request.
  • Evaluation was built to be hard to fool. Windows are split chronologically per student, 70/15/15, so the model is never scored on a question it has effectively already seen. Across 101k+ simulated attempts that gives 0.607 AUC against a 0.730 oracle ceiling, which is 83.2% of what was actually achievable on this data. Reporting the ceiling alongside the score matters more to me than reporting the score.
  • Around the model sit the pieces that make it a product: a 3PL IRT calibration layer, multi-stage test routing, an SM-2 derived review scheduler, a score projection from theta, and a mistake taxonomy that separates a genuine concept gap from a slip, a rush, a trap answer, or simple decay. 1,610 questions across 8 domains and 29 subskills, generated through an LLM-assisted pipeline (Azure OpenAI plus matplotlib figures) and all IRT-calibrated.
  • Shipped to 35 beta users recruited at random through social media, delivering ~11% larger weak-skill mastery gains and routing ~30% more practice toward weak skills than non-adaptive drilling.

NutriSnap

Nutrition tracker that helps students hit macro goals from dining-hall menus.

Year
2026
Scale
21 endpoints · 50+ users
Result
Menu load 1.8s → ~0.1s
  • A 21-endpoint Express 5 API over the six UW-Madison dining halls. Gemini 2.0 Flash identifies the dish from a tray photo, but it never estimates the macros. It only picks which menu item you're looking at, and the numbers come from the verified Nutrislice entry. A model guessing "roughly 40g protein" is worse than useless to someone actually tracking.
  • The recommender is a deterministic weighted-sum scorer, not a model. Every item gets 0 to 100 from five signals: macro fit against what you have left for the day (50), goal-specific shaping (20), learned preference from your own logs (20), familiarity (10), and a repeat penalty so the list stays varied (-15). No weights to train and no black box, which means when a recommendation looks wrong I can tell you exactly which term caused it.
  • The macro-fit curve peaks when an item covers 15 to 60% of what's left, tapers past that, and zeroes out if it overshoots by more than half. Goals reweight the macros rather than swapping the formula: cut puts 0.50 on calories, bulk puts 0.55 on protein.
  • Dietary restrictions are a hard filter applied before scoring, never a penalty, because Nutrislice overloads one icon field with two opposite meanings. Some icons assert a property (this is vegan), others flag an allergen (this contains dairy). So vegan and halal require a tag to be present, while dairy-free and gluten-free require an allergen tag to be absent. Treating them alike silently surfaces unsafe food, so there are two regression tests whose only job is catching that.
  • Menu load went from 1.8s to about 0.1s, a 94% cut, by fetching all six halls concurrently with per-hall fault isolation, warming an in-process cache at boot, and deduplicating items that appear in multiple halls. No ORM, no Redis, no build step. Deployed on Render and Cloudflare Pages for 50+ users.

WeTrack

Surfaces your own procrastination loops from browsing patterns.

Year
2025
Model
Zero-shot DistilBERT · 5-8-1 MLP
Result
Zero runtime ML dependencies
  • Records how long you actually spend per site, splits it into focused work versus distraction, and finds the time-of-day windows where you reliably drift. An MV3 capture layer built on the service worker, alarms, and idle detection logs activity without polling, and survives the service worker being killed, which Chrome does aggressively.
  • Most sites can be classified by hostname alone. The genuinely ambiguous ones, YouTube and Reddit and the like, go to a zero-shot DistilBERT classifier, so there is no per-site training data to collect. It runs on loopback, on your own machine. Browsing history is about as personal as data gets, and none of it leaves.
  • Shipping a model inside a browser extension usually means shipping a runtime with it, megabytes of ONNX Web or TensorFlow.js for one small prediction. So I trained the risk scorer as a 5-8-1 MLP in PyTorch on 3,000 synthesised sessions, then dumped the state dict to JSON. The entire model is 57 numbers and two matrix multiplies, so I rewrote the forward pass in about twenty lines of plain JavaScript. No runtime, no network call, and Vite inlines the weights at build time.
  • Then I compared it against the hand-written heuristic it was meant to replace, and kept the heuristic. It was both more accurate and easier to explain to the person whose habits it was judging. The distilled model stayed in the repo as the more interesting engineering answer and the wrong product one.
  • Began as recurr at MadHacks 2025, a weekend build that spotted recurring distraction loops and predicted upcoming risk windows. Rebuilt since around the MV3 capture layer, a Next.js dashboard for live and historical trends, and regression tests over the summary maths.

W/03 BuildFest · Team of three

Pit Crew

A project-aware agent for small software teams. It reconciles the plan with what GitHub says actually happened, so nobody has to keep a task board up to date by hand.

Year
2026
Team
Three engineers
My part
GitHub ingestion · plan API · GitHub App · backup
  • A plan and a repository drift apart, and a task board only notices when someone remembers to drag a card. Pit Crew keeps the team's brief, tasks, owners, dependencies, and milestones on one side and normalised GitHub activity on the other, then reconciles them: what state each task is really in, which milestones are slipping, which branches are about to collide, and what the plan should change. It is built as Next.js 16 and React 19 on the front, Hono, Zod, and PostgreSQL behind it, with a Railway-ready API and the dashboard on Vercel.
  • I built the ingestion layer, because a coordination tool is only as good as its facts. Webhooks are verified with an HMAC-SHA256 signature checked against the raw request bytes (re-serialising the JSON would change the hash) using a timing-safe comparison. Each delivery ID is claimed once at the database, a failed delivery can be retried, and anything already stored is a no-op. Events land in an append-only table whose Postgres trigger rejects updates and direct deletes, so the history cannot be quietly rewritten by the analysis built on top of it.
  • Backfill runs through the same path as live webhooks. When a repository is first connected, pull requests, branches, branch-unique commits, and changed files are imported from the REST API using the same normaliser and dedupe keys, so a second run inserts nothing and a webhook racing a backfill collapses into one event. Connecting is self-service through a GitHub App rather than pasted tokens: the OAuth state is hashed and expires in ten minutes, the user's token is encrypted at rest with AES-256-GCM, and later calls use one-hour installation tokens, so no personal access token ever reaches the browser.
  • Task state comes from rules, not a model. A merged pull request with nothing newer reads as complete, an open pull request or active branch reads as in progress, and no linked activity reads as not started, each carrying a confidence and the events behind it. Dependencies are walked in topological order with real cycle detection, so a task whose prerequisite has not started is marked possibly blocked, while one whose prerequisite is merely under way is not. A human override always wins, and the computed value is kept beside it. Five kinds of health signal sit on top: milestone slipping, dependency incomplete, must-have with no activity, plan and repository disagreeing, and possibly blocked.
  • Events reach tasks through task keys like PC-12, matched case-insensitively across the PR title, branch name, and commit message. Anything without a key goes to a model, and its links count toward state only at 0.8 confidence or higher, shown as AI-inferred and rejectable; lower-confidence ones wait in a review queue. That job is capped at 30 calls an hour on the smart tier before overflowing to the fast one.
  • Branch collisions are exact file overlap between active branches, computed from GitHub's three-dot compare against the default branch rather than by summing push payloads, which overcounts after a merge from main or a revert. Lockfiles are ignored by default, and the interface says collision risk, not conflict, because overlapping files do not guarantee one.
  • AI is optional by design. A two-tier router sends cheap jobs to a fast model and open-ended reasoning to a smart one across Groq, OpenAI, OpenRouter, Anthropic, or a Microsoft Foundry agent, with a daily token budget, a response cache, and an audit record for every call. With no key configured, everything falls back to rules. The Maintainer that answers what needs attention can only call six read-only tools, and every citation it returns is checked against real IDs that a tool actually returned. If it cites something invented, the answer is discarded and a rules-based one is returned instead. Replans are proposals, never edits: a suggested change has to validate against a strict five-operation schema, and accepting it creates a new plan version while rejected ones stay in history.
  • Around that: export and restore round-trip a whole project as NDJSON with a SHA-256 footer over every line, discovering tables by their project_id column so new tables travel without registration. The repository carries a 39-endpoint API contract, a 20-table base schema with 13 ordered migrations, and 17 backend test files that run against a real embedded Postgres. On the dashboard I built the project timeline, branches panel, link-review queue, and Maintainer panel.
